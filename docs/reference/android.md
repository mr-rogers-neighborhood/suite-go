# Android

The native side of Suite Go, and the three places it needs care.

## The SDK this project expects

`apps/go/android/variables.gradle` is generated by `cap add android` and committed. It carries the
versions the build compiles against:

| Setting                                  | Value  | Note                                                                              |
| ---------------------------------------- | ------ | --------------------------------------------------------------------------------- |
| `compileSdkVersion` / `targetSdkVersion` | 36     | The SDK platform must be installed                                                |
| `minSdkVersion`                          | 24     | Android 7.0                                                                       |
| Android Gradle Plugin                    | 8.13.0 | Wants build-tools 35, not whatever happened to be installed                       |
| Gradle                                   | 8.14.3 | Run it on JDK 17 or 21; a newer JDK fails with a message that never names the JDK |

A distribution that installs the SDK through its package manager makes the SDK directory root-owned,
which means Gradle cannot fetch a component AGP asks for. `pnpm doctor` reports the state, and a failed
build prints the exact `sudo sdkmanager` command for the missing component rather than a stack trace.

## The share intent

`android/app/src/main/AndroidManifest.xml` holds the only hand-edited part of the generated project:
the `ACTION_SEND` intent filter on `MainActivity`, which is what puts Suite Go in Android's share
sheet.

`cap sync` does not rewrite the manifest, so the edit survives. `cap add android` does not, so it does
not — regenerating the project loses it. If the filter ever disappears, the app simply stops appearing
in the share sheet, which is quiet enough to go unnoticed for a while.

## Why the app is a real APK in the dev loop

`pnpm android:watch` rebuilds and reinstalls an APK on every save, rather than serving a live-reload
WebView. The things being developed here are native-adjacent: an intent filter, a cold start, the
WebView's own WASM implementation. A live-reload session exercises none of them.

## Testing on GrapheneOS

The target device is a de-Googled Android, and that is a better signal than a stock one for this app:

- **Vanadium is the WebView.** Hardened Chromium with hardened_malloc. Loro is WASM, and if it runs
  there it runs anywhere.
- **No Play Services, no Play Integrity, no Firebase.** The no-telemetry promise is enforced by the
  platform rather than by discipline.
- **Per-app network permission** can be revoked entirely. The container must not assume it has a
  network — which it does not, because v0 has no transport.

Memory Tagging Extension on newer Pixels can surface latent native crashes the emulator will not
reproduce. That is a feature of the test, not a bug in the app.
